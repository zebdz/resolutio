From a vote to a
verifiable record.

A voter keeps an original receipt. A finished poll becomes an immutable record. A Bitcoin timestamp gives that record independently checkable evidence of when it existed.

01

Follow the lifecycle

Finishing a poll, sealing its data, and confirming a timestamp are separate milestones. A failure in the later work must not undo a committed vote or the poll’s finish.

  1. 01 →CastKeep the original receipt
  2. 02 →FinishClose voting atomically
  3. 03 →SealFreeze five sections
  4. 04 →SubmitReceive a pending proof
  5. 05 →ConfirmVerify Bitcoin evidence
  6. 06VerifyCheck the evidence

Record and receipt checks can start once a seal is available. Bitcoin timestamp verification needs a confirmed proof. Initial bundle delivery starts with the first usable proof, even while it is pending.

  1. 01
    VOTER → POLL TRANSACTION · PHASE 2

    Accept the whole ballot; return its receipt.

    Lock the poll row, re-read its state, and accept votes only while it is ACTIVE. Persist the complete ballot, exact cast times, one participant receipt secret, signing willingness, and the data needed to replay the same receipt.

    After commit → original receipt. The voter can save it. A confirmed email address enables receipt email delivery in Phase 6.
    What must be atomic?

    The secret is 32 random bytes per participant per poll. Multi-choice answers share that secret but derive different salts. Vote rows keep their original createdAt values.

    A repeated successful request returns the same receipt. Cleanup or email failure must not turn a committed ballot into a failed cast response. Signing willingness is stored independently from actual signatures.

  2. 02
    POLL TRANSACTION → POST-COMMIT HANDLERS · PHASES 2–3

    Close voting at one definite cutoff.

    Finishing takes the same poll-row lock. It commits FINISHED and finishedAt, then dispatches PollFinished to explicit sealing and notification handlers.

    Two independent follow-ups → build the seal, and notify participants that voting finished. Sealing failure must not suppress the finish notification.
    Why the shared lock matters

    A pre-check outside the transaction can go stale. Every vote writer and competing poll-state writer must coordinate on the same row. A stale update must never reopen a finished poll.

    Polls already finished before rollout remain unsealed. A null finishedAt marks those legacy polls as ineligible.

  3. 03
    SEAL TRANSACTION · DOMAIN: PHASE 1 / INTEGRATION: PHASE 3

    Capture a consistent snapshot and seal it.

    Read the full poll, participants, votes, metadata and protocol holdings. Build the five canonical sections, the vote Merkle tree, the manifest and its root digest. Save them together in one repeatable-read transaction.

    Output → immutable sealed record. External names, labels and consented phones are captured by the successful sealing attempt; metadataCapturedAt records that time.
    What changes between finishing and sealing?

    Metadata may change after finishedAt and before a successful seal. A failed sealing transaction may retry with newer metadata. Once a seal is saved, covered renderings always reuse its frozen contents.

    The snapshot includes archived questions and answers, attachment metadata, and holdings resolved at each participant’s snapshotAt. No network calls occur in this transaction.

  4. 04
    ANCHOR WORKER → OPENTIMESTAMPS CALENDARS · PHASE 4

    Submit the digest and store a pending proof.

    The worker sends the root digest to OpenTimestamps outside the database transaction. It validates that the returned proof commits to that digest and contains a usable pending attestation, then stores a SUBMITTED anchor.

    First usable proof → initial bundle delivery. Phase 6 sends the manifest, the recipient’s own leaves and paths, authorized labels, and available proof to confirmed-email participants.
    What does “pending” mean?

    The calendars accepted the commitment, but verified Bitcoin evidence is not yet available. Pending must remain visibly different from confirmed.

    A submission failure becomes a durable FAILED attempt, even with no proof and no submission time. Recovery retries it later. Participant bundles never contain the signer list, even for an admin recipient.

  5. 05
    RECOVERY WORKER → CALENDARS + BITCOIN VERIFICATION · PHASE 4

    Upgrade the proof, then verify it.

    Retrieve upgraded proof data and verify its Bitcoin attestation through the configured verification adapter. Only then store CONFIRMED, the confirmed proof, block height and block time.

    Output → confirmed timestamp evidence. The upgraded proof is downloadable later; successful initial bundle emails are not automatically resent.
    Which component establishes validity?

    The real provider adapter must parse OTS proof bytes, check their committed digest, and verify Bitcoin evidence. The domain enforces consistency and legal transitions using that evidence.

    Nonempty bytes and a status label are insufficient. Development simulations remain labeled; a stub anchor cannot become a Bitcoin confirmation. Production requires an explicit real provider.

  6. 06
    VOTER / VIEWER → INDEPENDENT VERIFIER · PHASES 5, 7–8

    Check the record; render covered results from it.

    A standalone CLI checks local exported files first. Hosted checks follow. An original receipt enables comparison with the cast-time ballot; a code alone checks inclusion in the current supplied record.

    Final results and all three protocols → sealed snapshot. The PDF footer points to record verification. Active polls remain preliminary; legacy finished polls remain explicitly unsealed.
Created at cast time

Original receipt

Secret code, poll/user IDs, original vote preimages and hashes, plus cast-time question, answer and poll labels.

Kept by the voter. Essential for detecting a changed ballot before sealing.

Created after finish

Sealed record

Five sections, canonical manifest and root digest. Contents are frozen and disclosed according to policy.

Kept immutably. Final covered outputs read this snapshot.

Upgraded over time

Timestamp proof

An OpenTimestamps .ots proof linking the record’s digest to timestamp evidence.

Pending → confirmed. Its proof bytes can evolve while the sealed record stays the same.

Race scenario A · vote gets the lock first
  1. Vote transaction sees ACTIVE.
  2. Complete ballot and receipt data commit.
  3. Finish transaction acquires the lock and closes voting.
  4. The accepted vote is included in the later seal.
Race scenario B · finish gets the lock first
  1. Finish transaction commits FINISHED.
  2. Vote transaction acquires the lock and re-reads state.
  3. The late ballot is rejected before persistence.
  4. No successful receipt is issued for that rejected ballot.
02

Five sections. One commitment.

Each section can be disclosed separately. The public manifest commits to all five without exposing their contents. Anonymous, named and open polls use the same record structure.

How a vote becomes a private, provable leaf

A multi-choice ballot produces several leaves. A leaf commits to pollId, questionId, answerId, userId, weight, castAt, salt. 

salt = HMAC-SHA256(decoded receipt secret, questionId + ":" + answerId)
leaf = SHA-256(0x00 || canonical vote preimage)
node = SHA-256(0x01 || decoded left hash || decoded right hash)
empty tree = SHA-256("")

Leaves sort by hash, then pair left-to-right. An odd node carries up unchanged. A path supplies sibling hashes and their sides, allowing one leaf to be checked without exposing other voters’ preimages.

Producer text is prepared as NFC, then serialized using JCS. Received evidence must already have exact canonical bytes; verification does not repair it. Weights use integer millionths internally and six-place decimal strings; holding shares preserve eight decimal places.

Who can see what?

Authorization is enforced before any record contents are serialized to a client.

register + all vote preimages canViewVoterNames Admin-only for anonymous polls. Receipt secrets are excluded.
signers canViewSignWillingness Admin-only for every poll type; excluded from participant email bundles.

Signing willingness has its own section. Include only voters with a non-null decision. A declining voter’s phone is null; a willing voter’s phone is present only if available. An empty signer list is still hashed. This records willingness, not actual signatures.
03

The anchor has its own lifecycle

The seal stays immutable while anchor attempts evolve. A seal can temporarily have no anchor; that is recoverable work. At most one anchor is active: any anchor not marked SUPERSEDED.

FAILED

A submission attempt failed. The first failure can have no proof and no submission time.

5 min15 min1 hour6 hours24 hours…

Due retry → submission attempt. Success becomes SUBMITTED; another failure advances backoff.

SUBMITTED

A validated pending proof commits to the requested digest. Bitcoin confirmation has not yet been established.

Upgrade + Bitcoin verification → CONFIRMED. Otherwise keep pending and poll again. Stale for more than three days → supersede.

CONFIRMED

The upgraded proof has verified Bitcoin evidence, with block height and time recorded.

Confirmed proof remains downloadable. The underlying record and digest do not change.

SUPERSEDED

Retain the old pending attempt as history. Create a fresh attempt for the same root digest.

Replace atomically. Save the old anchor’s supersession and the replacement’s SUBMITTED or FAILED state together.

04

A crash leaves discoverable work

A reconciliation worker runs every 15 minutes. It examines persisted state, so work can resume even if the process stopped before an event handler or delivery ran.

Finished, no seal

Find eligible finished polls and run the complete snapshot-and-save transaction.

Sealed, no active anchor

Submit the saved root digest. Never rebuild the record from current data.

Anchor work is due

Retry a failure or upgrade a pending proof. Supersede a stale pending attempt when required.

Initial bundle missing

Once a usable proof exists, create missing delivery records and claim pending first sends.

How overlapping workers stay safe

Immediate dispatch, scheduled recovery and verify-page nudges share a persistent per-poll claim with owner, expiry and an increasing fencing token. Saving results checks the current token inside the transaction; expired workers cannot overwrite newer work.

Network I/O occurs outside transactions and batches are bounded. A verify page nudges only its own stale pending anchor, no more often than every 10 minutes.

When an email delivery fails or its outcome is unknown

Each recipient has a unique delivery record per seal: PENDING → SENDING → SENT / FAILED / UNKNOWN. A claimed first send can succeed, fail, or be left with an unknown outcome after interruption.

Recovery handles missing or pending initial deliveries. It does not automatically resend SENT, FAILED or UNKNOWN deliveries. Exactly-once email delivery is not claimed.

05

Verification answers three different questions

The CLI checks exported files without the running application. OpenTimestamps tooling verifies timestamp evidence separately. Hosted checks use the same pure core, but independent tools avoid relying on the operator’s page.

01 / Record consistency

Do these contents match the commitment?

Available to anyone holding the relevant authorized sections and manifest.

  1. Reject unsupported formats and noncanonical bytes.
  2. Recompute disclosed section hashes.
  3. Hash the manifest and compare its digest with the digest committed in the proof.
02 / Original ballot comparison

Is the ballot I retained included?

Requires the original downloaded or emailed cast-time receipt.

  1. Recompute its original salted leaves locally.
  2. Compare the complete expected set with the supplied own leaves. Changed, missing or extra own leaves fail.
  3. Verify every Merkle path to the manifest’s votes root.
03 / Bitcoin timestamp

What timestamp evidence anchors this digest?

Requires a proof with verified Bitcoin evidence.

  1. Check that the OTS proof commits to the manifest’s digest.
  2. Verify the Bitcoin attestation with independent tooling.
  3. Report pending separately; never treat a simulated proof as Bitcoin confirmation.
Original receipt→vote leaves→Merkle paths→votes root→manifest→root digest→OTS / Bitcoin proof

Without the original receipt

A stored or pasted secret can check inclusion in the current supplied record. It cannot establish agreement with the original cast-time ballot: the operator knows the secret too.

A fresh receipt download is not independent cast-time evidence. Import receipt secrets locally; do not send them to the hosted verifier’s server.

What the timestamp establishes

Evidence that the committed bytes existed no later than the Bitcoin timestamp. It does not establish voter authorization, truthful metadata, correct tallies, or the actual finishing time.

An omitted or withheld path prevents a successful inclusion check; it is not a cryptographic proof of non-inclusion.

Answer labels, PDFs and attachment limits

Resolve answer labels from a hash-verified canonical poll section only when results policy permits access or the voter imports a retained copy. Otherwise display receipt labels as cast-time claims, with proven IDs.

Final covered results and all three protocol PDFs render from the saved sections. The signer protocol uses the separately protected signer section. A footer authenticates the referenced record, not the exact PDF bytes; a modified PDF can retain a valid footer.

Attachment metadata is committed in v1; attachment file contents are not. Public hashes alone cannot reveal or prove the correctness of undisclosed tally contents.
